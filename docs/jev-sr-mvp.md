# Jev 게시글 우선순위 분석기 MVP 구현 지시서

## 1. 목표

사용자가 게시글을 작성하고 제출하면 Jev가 게시글의 긴급도를 판단하여 다음 결과를 보여주는 웹 애플리케이션을 구현해줘.

- 최종 우선순위: Level 1~4
- 각 Level의 확률
- Jev 판단 신뢰도
- 판단에 참고한 세부 분석값

이 MVP의 핵심 검증 대상은 다음 한 문장으로 정의한다.

> 대상자 정보, 제목, 내용을 입력하고 제출하면 Jev가 게시글의 업무 긴급도를 4단계 확률로 판단할 수 있는가?

설계 제안으로 끝내지 말고 실행 가능한 애플리케이션, 테스트, README까지 완성해줘.

---

## 2. 사용자 흐름

1. 사용자가 게시글 작성 화면을 연다.
2. 다음 필드를 입력한다.
   - 대상자 정보
   - 제목
   - 내용
3. 사용자가 제출 버튼을 클릭한다.
4. 화면에 분석 중 상태가 표시된다.
5. 백엔드가 세 필드를 하나의 구조화된 상태로 만들어 Jev에 전달한다.
6. Jev가 우선순위 4단계와 각 단계의 확률을 반환한다.
7. 화면에 최종 Level과 확률을 표시한다.
8. 사용자는 초기화 버튼을 눌러 다른 게시글을 다시 분석할 수 있다.
9. 분석에 성공한 질의는 현재 브라우저 세션의 질의 목록에 추가된다.
10. 사용자는 질의 목록 화면에서 기본으로 최근 분석한 질의부터 확인하고, 우선순위순 정렬을 선택할 수 있다.

## 3. MVP 범위

### 반드시 구현

- 게시글 작성 화면
- 대상자 정보 입력
- 제목 입력
- 내용 입력
- 필수 입력값 검증
- 제출 버튼
- 제출 중 로딩 상태
- 중복 제출 방지
- Jev API 연동
- 4단계 우선순위 판단
- 각 Level의 확률 표시
- Jev 판단 신뢰도 표시
- 오류 상태와 재시도
- API 키가 없을 때 사용할 Mock 모드
- 핵심 단위 테스트 및 API 테스트
- 실행 방법을 설명하는 README
- 현재 브라우저 세션에서 분석한 질의 목록 화면
- 최신 분석순을 기본값으로 하는 정렬 기준 UI
- 우선순위순 정렬 선택 시 Level 1부터 Level 4까지 표시

### 구현하지 않음

- 배포 관련 기능
- 서버에 저장되거나 사용자 사이에 공유되는 게시글 목록
- 게시글 수정 및 삭제
- 데이터베이스 저장
- 로그인과 사용자 인증
- 실제 사용자 알림
- 사용자별 알림 임계치 설정
- 이메일·Slack·Teams 연동
- 게시글 카테고리 자동 분류
- 담당자 자동 배정
- 관리자 화면
- 통계 대시보드

알림 기능은 향후 확장 대상이다. MVP에서는 Jev가 반환한 Level별 확률과 신뢰도를 보존할 수 있는 응답 구조만 준비한다.

2026-09-21 사용자 요청으로 분석 완료 질의의 세션 목록을 MVP 범위에 추가한다. 데이터베이스나 브라우저 저장소는 사용하지 않는다. 목록은 현재 페이지 메모리에만 유지하며 새로고침하면 초기화된다.

2026-09-24 사용자 요청으로 우선순위순 정렬을 활성화한다. 기본 정렬은 최신 분석순을 유지한다. 우선순위순은 Jev가 선택한 Level 1→4 순으로 표시하고, 같은 Level에서는 최신 분석 시각순, 같은 시각이면 기록 ID 내림차순으로 표시한다. 정렬은 기존 결과만 사용하며 재분석하지 않는다.

## 4. 입력 화면

### 대상자 정보

- 필수 입력
- 한 줄 또는 여러 줄 텍스트
- 예시:
  - 전체 임직원
  - 인사팀 급여 담당자
  - 재무팀 사용자
  - 특정 지점 근무자
  - 김철수 사원

### 제목

- 필수 입력
- 최대 200자
- 예시:
  - 급여 계산이 완료되지 않습니다

### 내용

- 필수 입력
- 여러 줄 텍스트
- 예시:
  - 오늘 급여 계산을 실행했는데 처리 중 상태에서 30분 이상 넘어가지 않습니다. 급여 마감 업무를 진행할 수 없습니다.

### 제출 버튼

버튼 이름:

```text
Jev로 우선순위 분석
```

제출 중에는 버튼을 비활성화하고 다음 상태를 표시한다.

```text
Jev가 게시글을 분석하고 있습니다...
```

## 5. 우선순위 4단계

숫자가 낮을수록 더 긴급하다.

| Level | 이름 | 판단 기준 |
|---|---|---|
| Level 1 | 긴급 | 급여 계산·마감·지급 장애, 필수 기능 전면 중단, 즉시 대응하지 않으면 중대한 업무 피해 발생 |
| Level 2 | 높음 | 주요 기능 장애, 여러 사용자에게 영향, 업무 진행이 크게 제한되며 빠른 대응 필요 |
| Level 3 | 보통 | 일부 기능 문제, 제한된 사용자 영향, 우회 방법이 있거나 일반적인 확인 필요 |
| Level 4 | 낮음 | 사용법 문의, 정보 요청, 개선 요청, 단순 불편, UI 문제, 업무 중단이 없는 게시글 |

### 중요한 구분 예시

```text
“급여 명세서를 어디서 확인하나요?”
→ Level 4 예상
```

```text
“급여 계산이 멈춰 오늘 급여 마감을 할 수 없습니다.”
→ Level 1 예상
```

단순 키워드 매칭으로 판단하면 안 된다. “급여”라는 단어의 존재가 아니라 실제 급여 업무가 중단됐는지를 판단해야 한다.

## 6. Jev 입력 상태

Jev에는 세 입력값의 의미가 구분되도록 구조화된 텍스트를 전달한다.

예시:

```text
[게시글 대상자]
인사팀 급여 담당자

[게시글 제목]
급여 계산이 완료되지 않습니다

[게시글 내용]
오늘 급여 계산을 실행했는데 처리 중 상태에서 넘어가지 않습니다.
급여 마감 업무를 더 진행할 수 없습니다.
```

대상자 정보는 단순 부가 정보가 아니다. 영향 범위와 업무 중요도를 판단하는 문맥으로 사용한다.

## 7. Jev 질문 설계

### 최종 우선순위

Jev의 `Choice` 질문을 사용해 네 가지 Level 중 하나를 선택하게 한다.

개념적인 질문 구조:

```json
{
  "priority": {
    "type": "choice",
    "instructions": "Determine the operational priority of this post.",
    "criteria": {
      "level_1": "Immediate response required. Payroll processing or payment is disrupted, a mandatory function is unavailable, or delay can cause severe business impact.",
      "level_2": "Prompt response required. A major function is degraded, multiple users may be affected, or work is significantly restricted.",
      "level_3": "Normal response. The issue has limited impact, affects part of a workflow, or has a reasonable workaround.",
      "level_4": "Low priority. This is a how-to question, information request, improvement request, cosmetic issue, or minor inconvenience without operational interruption."
    }
  }
}
```

실제 요청 형식은 구현 시점의 TypeSafe 공식 문서를 확인한 뒤 작성해. API 필드와 SDK 사용법을 추측하지 마.

### 세부 판단값

최종 Level과 함께 다음 질문을 한 요청에서 독립적으로 분석해.

#### 급여 업무 중단 여부

```text
이 게시글은 급여 계산, 급여 마감 또는 급여 지급이
완료되지 못하거나 지연되는 실제 장애를 설명하는가?
```

결과: Noul 확률

#### 필수 기능 장애 여부

```text
이 게시글은 정상적으로 작동해야 하는 필수 업무 기능이
실행되지 않거나 완료되지 않는 장애를 설명하는가?
```

결과: Noul 확률

#### 업무 진행 차단 여부

```text
게시글 작성자 또는 대상자가 이 문제 때문에
현재 업무를 더 진행하기 어려운가?
```

결과: Noul 확률

#### 영향 범위

Choice 선택지:

- `individual`: 개인 또는 극소수
- `team`: 특정 팀이나 사용자 그룹
- `many_users`: 여러 팀 또는 다수 사용자
- `organization_wide`: 조직 전체
- `unknown`: 게시글만으로 판단 불가

세부 판단값은 우선순위를 코드로 다시 계산하기 위한 것이 아니다. Jev가 어떤 문맥을 감지했는지 화면에 보여주고, 향후 알림 정책을 구성하기 위한 데이터로 사용한다.

## 8. 결과 응답 모델

백엔드는 Jev SDK의 원본 응답을 프론트엔드에 그대로 노출하지 말고 내부 응답 모델로 변환한다.

```json
{
  "priority": {
    "level": "level_1",
    "label": "긴급",
    "confidence": 0.91,
    "probabilities": {
      "level_1": 0.87,
      "level_2": 0.10,
      "level_3": 0.02,
      "level_4": 0.01
    }
  },
  "signals": {
    "payrollDisrupted": 0.94,
    "requiredFunctionUnavailable": 0.86,
    "workBlocked": 0.92,
    "impactScope": "team",
    "impactScopeConfidence": 0.82
  },
  "analyzedAt": "2026-09-21T20:00:00+09:00",
  "provider": "jev"
}
```

확률은 가능하면 0~1 범위로 정규화한다.

## 9. 결과 화면

분석이 완료되면 제출 폼 아래에 결과 카드를 표시한다.

### 최종 결과

```text
Level 1 · 긴급
Jev 판단 신뢰도 91%
```

### Level별 확률

막대그래프로 네 Level을 모두 표시한다.

```text
Level 1 · 긴급    87%
Level 2 · 높음    10%
Level 3 · 보통     2%
Level 4 · 낮음     1%
```

선택된 Level만 표시하지 말고 네 Level의 확률을 모두 보여줘. 이것이 일반적인 단일 분류 결과와 Jev 확률 판단의 차이를 보여주는 핵심 UI다.

### 세부 분석

```text
급여 업무 중단             94%
필수 기능 장애             86%
업무 진행 차단             92%
영향 범위                  특정 팀
영향 범위 판단 신뢰도       82%
```

### 낮은 신뢰도

Level은 항상 네 단계 중 하나를 보여주되, 신뢰도가 설정 가능한 기준값보다 낮으면 다음 안내를 추가한다.

```text
판단 신뢰도가 낮습니다. 사람이 내용을 추가로 확인하는 것이 좋습니다.
```

MVP 기본 기준값:

```text
LOW_CONFIDENCE_THRESHOLD=0.60
```

이 기준값은 환경변수 또는 설정 파일에서 변경할 수 있게 한다.

## 10. Provider 구조

Jev 연동이 UI와 비즈니스 로직에 직접 결합되지 않게 Provider 인터페이스를 사용해.

개념적인 구조:

```python
class PriorityAnalyzer(Protocol):
    async def analyze(self, post: PostInput) -> PriorityAnalysis:
        ...
```

구현체:

- `JevPriorityAnalyzer`: 실제 Jev API 호출
- `MockPriorityAnalyzer`: API 키 없이 결정론적으로 동작

환경변수:

```text
PRIORITY_ANALYZER=mock|jev
TYPESAFE_API_KEY=
LOW_CONFIDENCE_THRESHOLD=0.60
```

`TYPESAFE_API_KEY`가 없는데 Jev 모드로 실행된 경우 원인을 알 수 있는 안전한 오류 메시지를 제공해. API 키 값을 로그나 화면에 노출하지 마.

## 11. 기술 구성

먼저 저장소와 `AGENTS.md`를 확인하고 기존 기술 구성이 있으면 이를 존중해.

저장소가 비어 있다면 다음 구성을 사용해.

- 프론트엔드: React, TypeScript, Vite
- 백엔드: Python 3.11 이상, FastAPI
- Jev 연동: 공식 `typesafe-sdk`
- 백엔드 테스트: Pytest
- 프론트엔드 테스트: 현재 구성과 잘 맞는 경량 테스트 도구

데이터베이스는 사용하지 않는다. 제출한 게시글과 분석 결과는 현재 화면에서만 유지한다.

## 12. API 예시

```text
POST /api/analyze-priority
```

요청:

```json
{
  "targetInfo": "인사팀 급여 담당자",
  "title": "급여 계산이 완료되지 않습니다",
  "content": "급여 계산이 처리 중에서 멈춰 마감 업무를 진행할 수 없습니다."
}
```

성공 응답은 문서의 결과 응답 모델을 따른다.

오류 응답은 최소 다음 상황을 구분한다.

- 필수 입력값 누락
- 입력 길이 초과
- Jev API 키 누락
- Jev 요청 시간 초과
- Jev 응답 형식 오류
- 일시적인 외부 서비스 오류

오류가 발생했을 때 임의의 우선순위를 만들어 반환하지 마.

## 13. Mock 모드

Jev API 키 없이 UI와 전체 흐름을 시연할 수 있도록 Mock Analyzer를 제공해.

Mock 모드는 최소 다음 사례에서 결정론적인 결과를 반환해야 한다.

- 급여 계산·지급 중단 → Level 1
- 필수 기능 전면 중단 → Level 1
- 주요 기능 오류 및 다수 사용자 영향 → Level 2
- 우회 가능한 일부 기능 오류 → Level 3
- 사용법·조회 방법 문의 → Level 4
- UI 글자나 색상 문제 → Level 4

Mock 결과임을 화면에 명확히 표시한다.

```text
Mock 분석 결과
```

실제 Jev 결과인 경우 다음처럼 표시한다.

```text
Jev 분석 결과
```

- 대상자 정보: 필수, 최대 500자

- 오류 메시지는 사용자가 수정할 수 있도록 구체적으로 표시

## 15. 테스트 사례

최소 다음 사례를 자동 테스트 또는 수동 검증용 샘플로 제공해.

### Level 1 예상

```json
{
  "targetInfo": "인사팀 급여 담당자",
  "title": "급여 계산이 멈췄습니다",
  "content": "급여 계산이 처리 중에서 넘어가지 않아 오늘 마감 업무를 진행할 수 없습니다."
}
```

### Level 2 예상

```json
{
  "targetInfo": "재무팀 전체",
  "title": "결재 문서 승인이 되지 않습니다",
  "content": "여러 팀원이 승인 버튼을 눌러도 처리되지 않아 결재 업무가 지연되고 있습니다."
}
```

### Level 3 예상

```json
{
  "targetInfo": "영업팀 사용자",
  "title": "고객 검색 조건이 초기화됩니다",
  "content": "검색 조건이 가끔 초기화되지만 다시 입력하면 조회할 수 있습니다."
}
```

### Level 4 예상

```json
{
  "targetInfo": "전체 임직원",
  "title": "급여 명세서 조회 방법 문의",
  "content": "지난달 급여 명세서는 어느 메뉴에서 확인할 수 있나요?"
}
```

### 추가 경계 사례

- 제목에 “긴급”이 있지만 실제로는 단순 문의
- “급여”가 포함되지만 장애가 아닌 사용법 문의
- “오류”라는 단어가 없지만 업무가 완전히 중단된 내용
- 대상자는 전체 임직원이지만 내용은 단순 공지 요청
- 내용이 짧거나 모호하여 신뢰도가 낮아야 하는 경우
- 한글, 영문, 숫자와 특수문자가 혼합된 게시글

## 16. 보안 및 개인정보

대상자 정보와 본문에 개인정보가 포함될 수 있다.

MVP에서는 다음 원칙을 지켜.

- 합성 데이터만 샘플로 제공
- 실제 사용자 개인정보를 저장하지 않음
- 입력 원문을 서버 로그에 기록하지 않음
- API 키를 코드나 저장소에 포함하지 않음
- `.env.example`만 제공
- 외부 API 호출 전 실제 사내 데이터 사용에 대한 보안 검토가 필요하다는 내용을 README에 명시

## 17. 완료 조건

다음 조건을 모두 만족하면 작업 완료다.

1. 대상자 정보, 제목, 내용을 입력할 수 있다.
2. 제출 버튼을 누르면 백엔드 분석 API가 호출된다.
3. Jev가 Level 1~4 중 하나를 선택한다.
4. 네 Level의 전체 확률이 화면에 표시된다.
5. Jev 판단 신뢰도가 표시된다.
6. 급여 장애, 필수 기능 장애, 업무 차단, 영향 범위가 표시된다.
7. 낮은 신뢰도 결과에 추가 확인 안내가 표시된다.
8. API 키가 없어도 Mock 모드로 전체 흐름을 실행할 수 있다.
9. Mock 결과와 실제 Jev 결과를 화면에서 구분할 수 있다.
10. Jev 오류 시 임의의 우선순위를 표시하지 않는다.
11. 핵심 입력 검증, Provider, 응답 변환 및 UI 흐름 테스트가 통과한다.
12. 빌드와 타입 검사가 통과한다.
13. README만 보고 프로젝트를 실행하고 데모할 수 있다.
14. 분석에 성공한 질의가 현재 세션의 질의 목록에 추가된다.
15. 질의 목록은 기본으로 최신 분석순으로 표시되며 실패한 요청은 추가되지 않는다.
16. 우선순위순 정렬을 선택하면 Level 1→4 순으로 표시되며, 같은 Level은 최신 분석순으로 표시된다.

## 18. 작업 방식

1. 현재 저장소와 적용되는 `AGENTS.md`를 먼저 확인해.
2. TypeSafe의 최신 공식 문서에서 Jev API와 SDK 형식을 확인해.
3. 구현 전에 짧은 작업 계획을 세워.
4. 특별한 차단 요소가 없다면 질문만 남기고 멈추지 말고 구현을 완료해.
5. 구현 후 관련 테스트, 타입 검사와 빌드를 실행해.
6. 마지막으로 변경사항을 스스로 검토해 요구사항 누락을 확인해.

완료 후 다음 내용을 보고해줘.

- 구현 결과
- 사용한 기술 구조
- 주요 파일
- Jev 질문 설계
- 실행 방법
- Mock 모드와 Jev 모드 전환 방법
- 테스트와 검증 결과
- 알려진 제약
- 향후 알림 기능을 붙일 수 있는 확장 지점
