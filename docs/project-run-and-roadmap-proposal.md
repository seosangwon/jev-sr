# Jev 게시글 우선순위 분석기: 실행 안내와 다음 단계 제안

작성일: 2026-09-24  
상태: 제안서. 현재 구현 범위는 [MVP 기획서](jev-sr-mvp.md), 검증 내역은 [검증 문서](verification.md)를 따른다. 아래의 다음 단계는 아직 구현되지 않았다.

## 1. 현재 제품과 이번 제안의 결론

현재 앱은 대상자 정보·제목·내용을 Jev 또는 Mock Provider로 분석해 Level 1~4, 네 확률, 판단 신뢰도와 세부 신호를 보여 준다. 분석에 성공한 질의는 `질의 목록`에 쌓이고 기본으로 최신 분석순으로 표시된다. 목록은 현재 페이지의 React 메모리에만 있으므로 새로고침하거나 탭을 닫으면 사라진다. 2026-09-24부터 우선순위순 정렬도 선택할 수 있다.

**추천 순서:** 우선순위순 정렬은 완료했다. 다음은 ① 목록 상세 보기 → ② 실제 판단 품질 평가와 낮은 신뢰도 검토 흐름 → ③ 저장·접근 권한 설계 → ④ 알림 정책·전송이다. 저장과 알림은 데이터 보존·접근 권한·운영 책임을 결정한 뒤 별도 범위로 추진한다.

여기서 `우선순위순 정렬`은 Jev가 이미 선택한 Level을 목록에 배열하는 기능이다. 게시글을 다시 분석하거나 Level을 코드로 재계산하는 기능이 아니다.

## 2. 프로젝트 실행 방법

### 준비

- Python 3.11 이상, Node.js 20 이상, npm, `uv`가 필요하다. 이 컴퓨터의 시스템 `python3`는 3.9이므로 백엔드에는 반드시 아래의 `.venv/bin/python`을 사용한다.
- 저장소 루트: `/Users/seosang-won/Documents/ChatGPT/jev-sr`
- 현재 컴퓨터에는 `.env`, Python 가상환경, 프론트엔드 패키지가 이미 있다. 새 컴퓨터나 의존성을 다시 설치할 때만 다음을 실행한다.

```sh
cd /Users/seosang-won/Documents/ChatGPT/jev-sr
uv sync --locked --group dev
npm ci --prefix frontend
```

### 실제 Jev 모드

기존 `.env`에는 사용자가 발급한 키가 등록되어 있고, 앞선 합성 데이터 연결 확인은 성공했다. 키를 소스 코드나 터미널 출력으로 확인할 필요는 없다. `.env`의 변수 이름과 설명은 루트 [.env.example](../.env.example)을 참고한다. 아래처럼 두 터미널에서 각각 실행한다.

터미널 1 — 백엔드:

```sh
cd /Users/seosang-won/Documents/ChatGPT/jev-sr
.venv/bin/python -m uvicorn backend.app.main:app --env-file .env --host 127.0.0.1 --port 8000
```

터미널 2 — 프론트엔드:

```sh
cd /Users/seosang-won/Documents/ChatGPT/jev-sr
npm run dev --prefix frontend
```

브라우저에서 <http://127.0.0.1:5173>을 연다. 상단에 `Jev 모드`가 표시되는지 확인하고, 합성 질의를 입력해 `Jev로 우선순위 분석`을 누른다. 결과의 네 확률과 신뢰도를 확인한 뒤 `질의 목록`으로 이동한다. 실제 사내 데이터는 외부 API 전송에 대한 보안 검토 전까지 사용하지 않는다.

### API 키 없는 Mock 시연

백엔드의 `--env-file .env` 부분을 빼고 실행하면 기본 Mock 모드로 시작한다. 프론트엔드 실행 명령은 같다. 화면에서 `Mock 모드`를 확인하고 `시연 예제`를 선택한다. 현재 셸에 Provider 관련 환경변수가 직접 설정되어 있다면 그 값이 우선할 수 있으므로, 화면의 모드 표시를 확인한다. Mock 예제는 고정 결과이며 실제 AI 성능을 입증하지 않는다.

### 실행 중 점검과 종료

- 백엔드가 8000 포트를 이미 쓰고 있다면 기존 프로세스를 확인한다. 프론트엔드가 5173 이외 포트를 제시하면 터미널에 출력된 주소를 이용한다. 개발 서버의 `/api` 프록시는 기본적으로 8000 포트를 바라본다.
- 백엔드 설정을 바꾼 후에는 백엔드를 재시작하고 브라우저를 새로고침한다.
- 각 터미널에서 `Ctrl+C`로 종료한다. 화면의 입력·결과·목록은 새로고침 시 초기화된다.
- 전체 실행 및 문제 해결은 [README](../README.md)에 정리되어 있다.

### 검증 명령

저장소 루트에서 실행한다. 브라우저 테스트는 별도의 8100/5273 포트에서 Mock 서버를 시작하며 실제 Jev 키를 사용하지 않는다.

## 3. 다음 단계 제안

| 순서 | 제안 | 해결할 문제 | 완료 기준 |
|---|---|---|---|
| 1 (완료) | 우선순위순 정렬 활성화 | 긴급 질의가 시간순 목록 아래에 묻힌다. | 기본은 최신 분석순 유지. 선택 시 Level 1→4로 정렬하고 같은 Level은 최신 분석순, 같은 시각이면 기록 순서로 결정한다. 기존 Jev 결과를 재사용하며 API를 다시 호출하지 않는다. |
| 2 | 목록에서 분석 상세 열기 | 현재는 목록의 Level·요약만 보고 네 확률과 세부 신호를 다시 확인할 수 없다. | 목록 항목을 선택하면 원래 입력과 네 확률, 신뢰도, 세부 신호, Provider와 분석 시각을 읽기 전용으로 볼 수 있다. 뒤로 가도 목록 정렬과 입력 작성 상태가 유지된다. |
| 3 | 판단 품질 평가와 검토 흐름 | Jev 연결 성공만으로 업무 우선순위 판단의 정확도를 알 수 없다. | 합성 또는 사용 승인을 받은 비식별 사례를 사람이 Level 1~4로 표기한다. Jev 결과와 비교해 Level 1 누락, Level 4 과잉 긴급화, 낮은 신뢰도 사례를 구분한다. 기준값 0.60의 적정성을 측정하고 변경 근거를 남긴다. |
| 4 | 저장·접근 권한 설계 | 현재 목록은 새로고침하면 사라져 공동 업무에 사용할 수 없다. | 저장 기간, 삭제 방식, 누가 어떤 질의를 볼 수 있는지와 원문 보존 필요성을 결정한다. 그 결정에 맞는 서버 저장 모델과 조회 API를 만든 뒤 권한·삭제·오류 테스트를 통과한다. |
| 5 | 알림 정책과 전송 | Level이 높아도 담당자가 화면을 열기 전에는 알 수 없다. | 평가 결과에 근거해 Level 확률·신뢰도·세부 신호로 정책을 정의하고, 낮은 신뢰도는 사람 검토 대상으로 둔다. 중복 전송 방지와 전송 실패 처리까지 검증한 후 채널을 연결한다. |

### 1~2단계: 목록을 실제로 쓰기 좋게

현재 `frontend/src/history.ts`가 `newest | priority` 정렬을 담당하고 `frontend/src/QueryList.tsx`에서 두 기준을 선택할 수 있다. 우선순위는 이미 Jev가 선택한 `priority.level`을 사용한다. 같은 Level에서는 `analyzedAt` 내림차순으로 정렬하고, 동률은 현재 기록 ID로 해결한다.

상세 보기는 이미 `App.tsx`가 보유한 `QueryRecord`의 입력과 분석 결과를 활용한다. 재분석 없이 저장된 결과를 표시하므로 비용이 발생하지 않는다. `현재 화면에서만 유지`되는 성질은 그대로이며, 상세 보기에서도 Mock/Jev 출처를 명확히 보여 준다. 우선순위 정렬과 상세 보기는 한 작업으로 묶거나 각각 작은 변경으로 나눠 검토할 수 있다.

### 3단계: AI 판단을 실제 업무 기준과 비교

TypeSafe의 `confidence`는 Choice 확률 분포의 집중도를 요약한 값이며 정답률이 아니다. 공식 문서도 기준값을 도메인과 실제 성능을 보고 조정하라고 안내한다. 따라서 성공한 API 호출 수보다 사람이 정한 기준과의 차이, 특히 Level 1을 낮게 분류한 사례를 먼저 추적하는 편이 유용하다. [TypeSafe Confidence](https://docs.typesafe.ai/confidence)

평가 과정은 `현재 방식 → AI 적용 → 기대 효과`로 정리할 수 있다.

| 단계 | 방식 |
|---|---|
| 현재 방식 | 몇 개의 질의를 사람이 읽고 Jev 결과가 그럴듯한지 판단한다. |
| AI 적용 | 합성·승인된 사례에 사람의 기대 Level을 기록하고 Jev를 일괄 호출해 결과·확률·신뢰도와 비교한다. |
| 기대 효과 | 어떤 종류의 업무 중단을 놓치는지, 낮은 신뢰도 기준을 어떻게 바꿀지 근거를 남길 수 있다. |

이 단계에서는 입력 원문을 일반 로그에 남기지 않는다. 개인정보·민감정보의 수집, 보존과 로그 제외를 먼저 정의한다. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 4~5단계: 저장과 알림을 도입할 조건

저장 방식은 기능 구현 전에 `한 사람의 임시 기록`인지 `여러 사람이 보는 업무 게시글`인지 정해야 한다. 후자라면 로그인, 접근 권한, 보존 기간과 삭제 정책이 함께 필요하다. 브라우저 저장소만 먼저 추가하면 현재 서버가 보호하지 않는 원문이 각 사용자 기기에 남는다. 따라서 저장 기능은 별도 요구사항으로 다룬다.

알림은 오분류 비용이 높다. 모델의 Level·확률·신뢰도·세부 신호를 보존하는 현재 응답 구조를 활용하되, 3단계 평가 결과를 본 뒤 실제 임계값과 사람 검토 조건을 결정한다. TypeSafe 역시 행동의 위험도에 따라 서로 다른 신뢰도 기준을 두도록 설명한다. [TypeSafe Confidence](https://docs.typesafe.ai/confidence)

## 4. 제안 범위와 결정 시점

우선순위순 정렬은 완료했다. 다음에는 목록 상세 보기를 완료하고 사용자 피드백을 받는 것을 권장한다.

저장·로그인·알림·외부 채널·배포는 원래 MVP의 제외 범위다. 이 제안서는 구현 허가가 아니라 다음 계획을 비교하기 위한 문서다. 특히 서버 저장 여부, 원문 보존 기간, 목록 접근 대상, 알림 대상과 조건은 실제 도입 시 별도 제품 결정이 필요하다.
